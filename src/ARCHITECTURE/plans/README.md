## 所有工作的完成定義

- 每張驗收表的必要案例均有測試結果或資料證據，未實作案例不能標記通過。
- 程式改動先定義 dataclass／schema 與公開介面；新增程式檔以 250–300 行為界，超出須拆分並附鄰近 README。
- 測試使用固定種子、最小離線資料與 `tmp_path`；正式資料可用性屬另外的整合驗收，不能讓單元測試依賴線上服務。
- 每次修改後以同一明確 Python 執行 Lint／pytest，保留 exit code、測試摘要、revision／工作區差異、`sys.executable` 與依賴版本。可用 `rtk proxy .venv/bin/python -m ruff check .` 與 `rtk proxy .venv/bin/python -m pytest -q`；P0 修正入口一致性後，一鍵腳本也須得到相同結果。
- 初次基線在 Python 3.9 是 310 通過、1 個日曆案例失敗；本輪 `verify.sh` 使用 Python 3.13 卻是 311 通過。已確認同一 `.venv` 有不同 Python／日曆套件版本，詳見 P0；不能僅用其中一路通過就宣告環境一致性驗收完成，也不能刪除或 skip 該案例。
- 資料／報告雜湊與業務鍵必須完全相符；浮點數另按各計畫的容忍度判定，拒絕 NaN／Inf 冒充有效值。
- 產出驗收紀錄 `acceptance.json`，至少列 `work_id, revision, environment, case_id, status, evidence_path, checked_at`；實際產物可放 `artifacts/acceptance/<work_id>/<run_id>/`。
- 工作狀態使用 `planned / in_progress / awaiting_external / failed / accepted`；只有全部必要案例通過才是 `accepted`。取得方案完成與資料補齊完成分開登記。
