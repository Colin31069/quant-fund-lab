### P0：先建立可重現的測試基線

目前環境的 `exchange-calendars` 為 `4.5.6`。失敗測試預期 `2025-01-09` 不屬缺漏交易日，但目前套件將它列為預期交易日。初次盤點只記錄差異；本輪已核對 [ICE／NYSE 官方公告](https://ir.theice.com/press/news-details/2024/The-New-York-Stock-Exchange-Will-Close-Markets-on-January-9-to-Honor-the-Passing-of-Former-President-Jimmy-Carter-on-National-Day-of-Mourning/default.aspx)，確認該日休市。具體修正選擇與必要案例見[P0 執行計畫](plans/P0_CALENDAR.md)。

本輪再確認 `.venv/bin/python` 是 Python 3.9.6／日曆 4.5.6，而 pytest entrypoint 指向同一 `.venv` 的 Python 3.13.13／日曆 4.13.2，後者完整測試通過。P0 先消除 runtime 混用並建立可重建環境，不能將較新版本已通過解讀為兩條執行路徑都已修復。

續查發現兩個 runtime 的安裝 metadata 仍是 `0.11.6`，Python 3.13 甚至無法直接匯入專案；pytest 的 `pythonpath=["src"]` 掩蓋了匯入差異。P0 的驗收須包含乾淨安裝後在 repo 外匯入及原始碼／安裝版本相符，不能只跑 pytest。

1. 核對交易所公告與套件支援範圍，決定更新依賴或建立有來源的例外資料。
2. 固定可重建的依賴集合，保存 Python／套件版本與日曆來源版本；新增版本須確認專案 Python 相容性。
3. 日曆邊界、臨時休市與缺漏交易日採離線測試，保留缺資料會被辨識的契約。

### M12-4：研究就緒檢查與修復清單

既有版本已有批次預覽、問題分類、缺檔 CSV 與按期間彙總。此次新增的是穩定問題代碼、明確相依關係，以及與研究執行共用的就緒判定。

先定義以下公開契約，再編寫邏輯；均為待新增型別：

| 型別／介面 | 必要資訊或行為 |
| --- | --- |
| `FindingCode` | 穩定代碼區分缺月檔、缺交易日、覆蓋不足、未建模事件、來源衝突與暖機不足；顯示文字可獨立修改 |
| `ReadinessFinding` | 問題 ID、代碼、標的、日期範圍、佐證參照、`depends_on`；不靠顯示文字辨認問題 |
| `PeriodReadiness` | 要求／實際資料範圍、暖機需求／已驗證數量、阻擋問題 ID、`ready/blocked/unknown` 狀態 |
| `StudyReadiness` | schema 版本、資料與檢查規則指紋、各期判定、全部原始問題及研究限制 |
| `assess_study_readiness()` | 純讀取，輸入已準備資料與明確期間設定；同時供 UI、研究執行與報告使用 |

`ready` 只代表明列檢查通過；資料發布時點未證實、固定現存股票池與成交代理等限制仍須隨報告呈現。無法判定的必要資料採 `unknown` 並阻擋相依期間。

驗收案例：

- 所有原始問題均可追溯；彙總與相依標記不能消除阻擋條件。
- 補價量檔後重新檢查，缺少企業行動審核仍阻擋；基準與交易標的採同等要求。
- 同時缺少整日行情時，不能以縮短觀測序列當成完整暖機；所需交易日依據不足時明確阻擋。
- 以最小離線測試資料驗證分期缺檔計數及跨期暖機依賴；本機盤點數量可由實際清單重算。
- 修復清單列出「缺什麼、影響哪一期、需何佐證、重查結果」，既有來源衝突與雜湊檢查維持有效。
- 新增問題格式使用明確 schema；舊凍結研究仍按原格式驗證，不能回寫舊 manifest 或補造審核紀錄。

### M12-5：讓官方資料真正可供研究

1. 依 M12-4 清單先補開發期 31 份月檔；資料取得沿用既有人工匯入或經同意的下載流程。
2. 分別完成五類企業行動覆蓋審核，逐日缺價須有價量檔或停牌／休市依據；實際重新檢查後才關閉問題。
3. 核對未建模事件。若需認股權、增資或減資模型，先定義權利數量、成本、資金支用日及資訊可得時間，再接入帳務；必要資料未知時繼續阻擋。
4. 開發期完成後，再依序補驗證期 132 份及歷史評估期 242 份，連同各自暖機重新驗證。

驗收以每一期「必要檢查無未解阻擋、至少 120 個完整暖機交易日、來源／審核證據可驗證」為準。若需改變股票池或研究範圍，建立新協議與新 study ID，記錄原因及既有資料接觸情況；不能在看過結果後刪股並維持原研究身分。

實際零股歷史價量、交割日曆及券商資金規則列為資料可行性調查；取得可驗證資料後才能提升模型精度。目前代理模型的結果仍以既有假設解讀。

### M13：可驗收的研究程序

- **M13-1 協議與登記**：凍結股票池、期間、暖機、選參用途、策略／候選集合、風險與成本假設、來源指紋、程式／依賴版本及隨機種子。保留所有實驗與既有資料接觸紀錄；`holdout_untouched` 不能只靠 checkbox 變成獨立樣本證明。
- **M13-2 可比較的基準**：保留現有 ensemble、momentum、同股票池等權，以及 0050 無成本參考；另增加採相同資金、零股費用與交割假設的可交易基準，避免把不同成本口徑直接排名。
- **M13-3 決策報告**：延用既有成本／成交比例敏感度，新增資金使用率、未成交原因、止損嘗試至實際退出的延遲，以及實現虧損超過事前風險預算的幅度。已完成交易、未平倉與未結算分列。
- **M13-4 評估紀律**：開發期選擇候選，驗證期按預先規則檢查；2025 年後已接觸資料維持探索性。未來前向觀察另凍結協議及開始日；任何看過結果後的改參另開實驗。

驗收要求同一凍結輸入的數值結果可重現、報告完整性通過、基準口徑明確、所有候選有紀錄。少於 30 筆已完成交易維持樣本不足標記；超過此數也不能直接認定策略有效。現有 walk-forward／robustness 元件要先驗證與零股成交及交割語義相容，再接入。

### M14：零股持久化模擬與每日增量

一般 `PaperLedger` 已有完成標記、交易原子性、設定與資料指紋鎖定及獨立稽核。零股的 `study_ledger.sqlite` 目前只是研究帳戶存檔；M14 必須先定義專用狀態與相容契約。

- 持久保存止損／追蹤止損、退出重試、當日到期委託、部分成交、買款保留、賣款應收與未結算應付。
- 單日帳務與完成標記同一 SQLite transaction 提交；來源 snapshot 另外做可驗證鏈結。
- 增量資料與新訊號只能增加未完成日；已提交日的資料、訊號及執行假設變動須拒絕續跑，不能重新選參後覆蓋歷史。
- 零股帳務獨立核對 cash、payables、receivables、positions、NAV 與風險狀態；沿用經驗證的共享撮合／成本元件。
- 既有一般帳本與研究存檔保持可讀；如需遷移，另定可審計流程及測試。

驗收以一次完成對照分段續跑，並注入成交後、交割後、NAV 後與完成標記前的故障；恢復後全部帳務、訂單、止損狀態及日末指紋一致。模擬繼續限定虛擬資金。
